# Redesign Existing Projects — адаптированная методика

## Алгоритм

**1. Исследовать** существующий код, UI-компоненты, стиль, экраны, API и пользовательские сценарии. Ничего не менять на этапе диагностики.

**2. Составить аудит** с подтверждёнными наблюдениями:
- информационная архитектура и навигация;
- визуальная иерархия, типографика, расстояния, сетка;
- консистентность цветов, форм, таблиц и кнопок;
- мобильные состояния и доступность;
- loading / empty / error / disabled / success;
- перегруженные шаги и неочевидные действия;
- технические и продуктовые риски изменений.

Каждая проблема: **где находится → почему мешает → предложение → приоритет P0/P1/P2 → риск изменения**. Не называть субъективный вкус объективным дефектом.

**3. Подготовить план** маленьких независимых правок с критериями приёмки. Для запросов исключительно на аудит не изменять файлы. При прямой задаче на реализацию двигаться по согласованному объёму.

**4. Внести изменения** в текущем стеке, минимальными diff. Не заменять сложную таблицу красивыми карточками, если сотрудники теряют возможность сравнивать строки. Не менять API, формат данных, SQL, формулы, роли пользователей или бизнес-процессы ради дизайна.

**5. Проверить** существующие функции, сборку, тесты, мобильный сценарий, клавиатуру, состояние ошибок, визуальные регрессии.

## Приоритеты

1. Блокирующая функциональность и ошибки доступности.
2. Понятность главного действия, критических данных и навигации.
3. Мобильное использование и интерактивные состояния.
4. Единообразие компонентов, сетки, типографики.
5. Анимации и второстепенная визуальная полировка.

## Ограничения

- Фирменный стиль и актуальный UI-kit — приоритетнее вкусовых запретов сторонних авторов.
- Не заставлять все проекты использовать один шрифт или одинаковую темную палитру.
- Не вводить новые зависимости без необходимости.
- Не придумывать метрики, цены, клиентов, отзывы и данные таблиц.
- Сохранять возможность отката и фиксировать то, что протестировано.
