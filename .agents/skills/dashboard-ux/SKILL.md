# Dashboard UX

## Цель

Управленец за несколько секунд находит отклонение и понимает, где действовать. Оператор выполняет повторяющуюся задачу с минимальным количеством кликов. Красота не должна уменьшать плотность полезных данных.

## Контекст перед проектированием

- Роль пользователя и частота сценария.
- Главные управленческие вопросы: что произошло, где, почему, кто отвечает, что делать дальше.
- Источник каждого показателя, период, фильтры, единица измерения, метод расчёта.
- Права доступа, ограничения по отображаемым данным.
- Десктопный сценарий и минимально полезный мобильный сценарий.

## Правила KPI

- Надпись, значение, единица измерения, период и изменение к базе сравнения должны быть явно связаны.
- «Нет данных», «0», «не рассчитано» и «ошибка загрузки» различаются.
- Цвет — дополнительный, а не единственный сигнал статуса.
- На графиках понятны оси, легенда, период, нули и границы.
- Не вводить статистически сомнительные красно-зелёные «планы» без правил интерпретации.
- Не менять формулы, агрегацию, округление и единицы в рамках UX-задач.

## Таблицы

- Сохранять полезную плотность: выравнивание чисел справа, табличные цифры, фиксированные единицы и понятные заголовки.
- Большие таблицы: сортировка, фильтр, экспорт, пагинация/виртуализация — по реальной потребности.
- При раскрытии региона или объекта сохранять контекст периода и фильтра.
- Указание применённых фильтров и возможность сбросить их.
- Sticky header / колонка — только если они реально улучшают сценарий и не мешают мобильной прокрутке.
- Проверять длинные названия городов, объектов и организаций.

## Мобильный режим

Выбирать для каждой задачи один из подходов:
1. Компактная таблица с предсказуемой горизонтальной прокруткой и подсказкой.
2. Группированные строки со вторичными деталями по раскрытию.
3. Карточки, если сравнение значений между строками не критично.

Нельзя скрывать ключевые показатели ради адаптивности без продуктового решения. Не допускать горизонтальной прокрутки всего документа без необходимости.

## Состояния и доступность

Проверять: скелетон, пустой период, ошибка API, частичный ответ, загрузка экспорта, отключённый фильтр, отсутствие прав, длинные данные. Формы, кнопки и таблицы должны управляться с клавиатуры.

## Проверка результата

Попросить подтвердить три реальные задачи пользователя: найти объект с падением выручки, сравнить периоды, разобраться с проблемной строкой. Проверить на телефоне и десктопе; сравнить числа с исходным API или тестовыми фикстурами.

**Нельзя менять расчёты и источники данных без отдельного задания.** Для дизайна использовать \`docs/design-system.md\`.
